#  1. CIFRADOS SIN USO DE LLAVES
####################################################################################################
=== Funcion hash criptografica (SHA-256) ===
Propiedad proporcionada : Integridad (deteccion de cambios) SI el valor hash llega por un canal/medio confiable; NO proporciona confidencialidad ni autenticacion de origen por si sola.
-- Entradas --
   mensaje: 5472616e73666572697220313030207065736f73206120426f622c206375656e...(+12 chars)
-- Info. PÚBLICA (sí viaja) --
   huella_sha256: 15485a525dc2b7b498110d10da6dad0dcac0fa3c6428f43a26512b8ba433df6a
-- Salidas --
   huella_sha256: 15485a525dc2b7b498110d10da6dad0dcac0fa3c6428f43a26512b8ba433df6a
   tamano_salida_bits: 256
-- Recursos --
   tiempo_ejecucion_ms: 0.0252
   memoria_pico_python_bytes: 97
   memoria_nota: Medida solo con tracemalloc (objetos Python); no incluye asignaciones nativas de OpenSSL/libcrypto.
   tamano_entrada_bytes: 38
   tamano_salida_bytes: 32
-- Condiciones de uso --
   * SHA-256 es resistente a colisiones y a preimagen con el estado del arte actual.
   * NUNCA debe usarse sola para proteger contrasenas (es demasiado rapida: permite probar miles de millones de intentos por segundo). Usar una KDF (Scrypt/Argon2).
   * El valor hash debe llegar al receptor por un canal cuya integridad este garantizada de otra forma (ej. HTTPS, o publicado junto con una firma digital).

=== Construccion esponja / XOF (SHAKE-256) ===
Propiedad proporcionada : Integridad / huella de longitud variable. Sigue sin llave: no da confidencialidad ni autenticacion por si sola. Es la base interna de mecanismos modernos como KMAC o de generadores de mascara.
-- Entradas --
   mensaje: 5472616e73666572697220313030207065736f73206120426f622c206375656e...(+12 chars)
   longitud_salida_pedida_bytes: 32
-- Componentes --
   tasa_absorcion/capacidad: fijas por el algoritmo (no configurables por el usuario)
-- Info. PÚBLICA (sí viaja) --
   salida_xof: 8755a9eb2b2b433838868c04c34b613f13da3228eec30c441e47264ca6d1b31e
-- Salidas --
   salida_xof: 8755a9eb2b2b433838868c04c34b613f13da3228eec30c441e47264ca6d1b31e
   tamano_salida_bytes: 32
-- Recursos --
   tiempo_ejecucion_ms: 0.0128
   memoria_pico_python_bytes: 97
   memoria_nota: Medida solo con tracemalloc (objetos Python); no incluye asignaciones nativas de OpenSSL/libcrypto.
   tamano_entrada_bytes: 38
   tamano_salida_bytes: 32
-- Condiciones de uso --
   * La seguridad contra colisiones de una salida de N bytes es como maximo min(N,32) bytes efectivos de resistencia (para SHAKE-256), por eso para 256 bits de seguridad se piden al menos 32 bytes de salida.
   * Util para derivar varias subclaves de distinta longitud a partir de un mismo secreto (a diferencia de un hash de salida fija).

#  2. CIFRADOS SIMETRICOS

=== Cifrado simetrico por bloques (AES-128-CBC) ===
Propiedad proporcionada : Confidencialidad UNICAMENTE. CBC por si solo NO protege integridad: un atacante puede alterar bytes del cifrado y, salvo que rompa el relleno del ultimo bloque, Bob 'descifrara' datos corruptos sin ninguna alerta.

-- Componentes --
   llave_AES_128: 7cce6d6a0ec1c9d7729299997e29b7e0
   IV_16B: c99cdd0f1998e95bc21b65a3200316db
   relleno: PKCS7
-- Info. SECRETA (no viaja) --
   llave_AES_128: 7cce6d6a0ec1c9d7729299997e29b7e0
-- Info. PÚBLICA (sí viaja) --
   IV_16B: c99cdd0f1998e95bc21b65a3200316db
   texto_cifrado: cb1ef2896107f90431866409025caf87fa686423f00a2b2d8ebf8d5dfd8173a3...(+32 chars)
-- Salidas --
   texto_cifrado: cb1ef2896107f90431866409025caf87fa686423f00a2b2d8ebf8d5dfd8173a3...(+32 chars)
-- Recursos --
   tiempo_ejecucion_ms: 0.8179
   memoria_pico_python_bytes: 6590
   memoria_nota: Medida solo con tracemalloc (objetos Python); no incluye asignaciones nativas de OpenSSL/libcrypto.
   tamano_entrada_bytes: 38
   tamano_salida_bytes: 48
-- Condiciones de uso --
   * El IV debe ser impredecible y NUNCA reutilizarse con la misma llave.
   * La llave debe mantenerse secreta; si Eve la obtiene, pierde toda confidencialidad (ver escenario explicito de fuga de llaves).
   * NO usar CBC solo para datos donde la integridad importe: combinar con un MAC (Encrypt-then-MAC) o usar un modo AEAD como AES-GCM.

=== Cifrado por flujo (ChaCha20) ===
Propiedad proporcionada : Confidencialidad unicamente (como CBC, sin autenticacion). Un cifrado de flujo genera un 'keystream' pseudoaleatorio y lo combina con XOR: cualquier bit que Eve voltee en el cifrado voltea EXACTAMENTE ese mismo bit en el texto claro recuperado, sin error ni aviso.
-- Entradas --
   mensaje: 5472616e73666572697220313030207065736f73206120426f622c206375656e...(+12 chars)
-- Componentes --
   llave_256bits: bee9cb36eb1b20613d5d8a67ca3b22819922b0910ba2a347f75429a971a13d57
   nonce_128bits(incluye_contador): 28113bd23d46c58e0e8253d400b8f8a0
-- Info. SECRETA (no viaja) --
   llave_256bits: bee9cb36eb1b20613d5d8a67ca3b22819922b0910ba2a347f75429a971a13d57
-- Info. PÚBLICA (sí viaja) --
   nonce: 28113bd23d46c58e0e8253d400b8f8a0
   texto_cifrado: ce331bd3f5dd5068cc219b18934a15ebdfcd10aad01453bf05abfbf6a163fd1b...(+12 chars)
-- Salidas --
   texto_cifrado: ce331bd3f5dd5068cc219b18934a15ebdfcd10aad01453bf05abfbf6a163fd1b...(+12 chars)
-- Recursos --
   tiempo_ejecucion_ms: 0.0591
   memoria_pico_python_bytes: 5673
   memoria_nota: Medida solo con tracemalloc (objetos Python); no incluye asignaciones nativas de OpenSSL/libcrypto.
   tamano_entrada_bytes: 38
   tamano_salida_bytes: 38
-- Condiciones de uso --
   * El par (llave, nonce) JAMAS debe repetirse: reutilizar un nonce con la misma llave rompe por completo la confidencialidad (permite recuperar el XOR de dos mensajes).
   * No proporciona integridad: en la practica se usa casi siempre dentro de un AEAD (ChaCha20-Poly1305), nunca 'pelado' como aqui, que es solo con fines didacticos.

#  3. CIFRADOS ASIMETRICOS
####################################################################################################
=== Cifrado de clave publica (RSA-2048-OAEP) ===

#  4. LAS NUEVE DEMOSTRACIONES DE ATAQUE / MANIPULACION (incluye ataque de diccionario)
####################################################################################################
Escenario: Contrasena debil (ataque de diccionario contra SHA-256 directo)
Huella objetivo (SHA-256): 0e44ce7308af2b3de5232e4616403ce7d49ba2aec83f79c196409556422a4927
Intentos probados: 15/16  |  Tiempo total: 0.008 ms (~0.00056 ms/intento)
Resultado: CONTRASENA ENCONTRADA -> P@ssw0rd!
Aprendizaje: Eve NO 'descifro' el hash (SHA-256 no se puede invertir); recreo el mismo calculo que hizo el sistema y comparo resultados. 'Adivinar por fuerza bruta/diccionario' es un ataque totalmente distinto, y mucho mas rapido de ejecutar, a 'romper criptograficamente' el algoritmo.
------------------------------------------------------------------------------------------
Escenario: Derivacion de contrasenas (SHA-256 directo vs Scrypt, mismo diccionario de 16 palabras)
Tiempo total probando el diccionario completo contra SHA-256 directo : 0.006 ms
Tiempo total probando el diccionario completo contra Scrypt (N=2^14) : 416.776 ms
Scrypt fue ~64497x mas lento de atacar con el mismo diccionario.
Aprendizaje: los PARAMETROS DE COSTO (iteraciones en PBKDF2; N,r,p en Scrypt) multiplican directamente el trabajo que Eve debe invertir POR CADA intento del diccionario; con SHA-256 'pelado' ese costo es practicamente nulo.
------------------------------------------------------------------------------------------
Escenario: Cifrado SIN autenticacion (AES-CBC)
Mensaje original            : b'Transferir 100 pesos a Bob, cuenta 001'
Bob 'descifra' sin error?   : SI (accepted=True)
Mensaje que Bob obtiene     : b'O\x95\x00\xc6\xab\xd8);\x10m\xd0/\xfc\xf9\xb2\x92eso\x8c a Bob, cuenta 001'
Aprendizaje: el cifrado por si solo NO garantiza deteccion de modificaciones. Bob no recibe ningun error ni alerta; simplemente obtiene datos distintos a los que Alice envio, y los trata como legitimos a menos que el mensaje tenga ademas un mecanismo de integridad.
------------------------------------------------------------------------------------------
Escenario: Cifrado AUTENTICADO (AES-GCM) con el mismo tipo de manipulacion
Mensaje original          : b'Transferir 100 pesos a Bob, cuenta 001'
Bob acepta el mensaje?    : NO -> RECHAZADO
Detalle                   : Etiqueta de autenticacion invalida: el mensaje fue modificado (o la llave/nonce/AAD no coinciden). AES-GCM RECHAZA el mensaje completo; no entrega texto claro parcial.
Aprendizaje: la verificacion DEBE fallar (y falla) ante cualquier bit alterado del cifrado, del nonce o de los datos asociados. A diferencia de CBC solo, GCM detecta la manipulacion y Bob rechaza el mensaje completo en vez de usar datos corruptos.
------------------------------------------------------------------------------------------
Escenario: HMAC/CMAC - Eve modifica el mensaje SIN conocer la llave
Mensaje original  : b'Orden de compra #4521: 10 unidades'  -> verificacion: ACEPTADO
Mensaje alterado  : b'Orden de compra #4521: 99 unidades'  -> verificacion: RECHAZADO
Aprendizaje: sin la llave, Eve no puede recalcular una etiqueta valida para el mensaje modificado; la etiqueta original deja de ser valida y Bob rechaza el mensaje.
------------------------------------------------------------------------------------------
Escenario: Firma digital - se modifica un mensaje firmado
Verificacion con mensaje original : ACEPTADA
Verificacion con mensaje alterado : RECHAZADA
Aprendizaje: la firma deja de verificarse ante CUALQUIER cambio en el mensaje, incluso sin conocer la llave privada de Alice; esto se debe a que la firma cubre criptograficamente el contenido completo (via su huella hash).
------------------------------------------------------------------------------------------
Escenario: Acuerdo de llaves (ECDH) SIN autenticacion, con Eve sustituyendo valores publicos
Llave de Alice == llave de Bob (lo que ambos CREEN compartir)?  False
Llave de Alice == llave que Eve establecio con Alice?            True
Llave de Bob   == llave que Eve establecio con Bob?              True
Aprendizaje: Alice y Bob NUNCA llegan a compartir la misma llave entre ellos; cada uno establece, sin saberlo, una llave DISTINTA con Eve. Eve puede descifrar, leer, re-cifrar y reenviar todo el trafico sin que ninguno lo note. Un acuerdo de llaves necesita autenticar a los participantes (firmar las llaves publicas, o usar certificados/PKI) para impedir esto.
------------------------------------------------------------------------------------------
Escenario: Repeticion de mensajes (replay) sobre un mensaje autenticado con HMAC
Etiqueta HMAC del mensaje reenviado sigue siendo valida? SI
Receptor SIN control de repeticion -> acepta la transferencia repetida? True
Receptor CON control (numero de secuencia / nonce ya visto) -> 1ra vez: True, 2da vez (repetida): False
Aprendizaje: la autenticacion por si sola (HMAC, CMAC, firma) prueba que el mensaje es genuino y no fue alterado, pero NO dice nada sobre si ya se proceso antes. Se necesitan controles adicionales (numeros de secuencia, nonces de un solo uso, marcas de tiempo con ventana de validez) para impedir que un mensaje valido capturado se reenvie con exito.
------------------------------------------------------------------------------------------
Escenario: PKI - se presenta un certificado de una CA NO confiable
Certificado emitido por la CA confiable  -> Bob lo acepta? True
Certificado emitido por la CA del atacante (mismo 'sujeto': bob@servidor.edu) -> Bob lo acepta? False
Motivo del rechazo: La firma del certificado NO corresponde a ninguna CA del almacen de confianza de Bob. El certificado pudo ser emitido por una CA desconocida/no confiable (p. ej. una CA que Eve controla). Bob debe RECHAZARLO.
Aprendizaje: aunque el certificado falso tenga el mismo 'nombre' de sujeto y una firma VALIDA (valida respecto a la CA del atacante), el receptor debe rechazarlo porque esa CA no esta en su almacen de confianza. La seguridad de la PKI depende por completo de que lista de CAs decide confiar cada receptor.
